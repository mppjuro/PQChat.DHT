# Polling Lifecycle and Background Execution on Android (PQChat DHT)

This document describes the architecture of the polling lifecycle state machine, resilience against process freezing under Android 12+ (Cached App Freezer), Foreground Service `dataSync` limits under Android 15 (targetSdk 35), and background task restoration following device reboots (`BOOT_COMPLETED` + WorkManager).

---

## 1. 4-State Polling State Machine Architecture

In accordance with [AGENTS.md](file:///c:/Users/PJURO/PQChat.DHT/AGENTS.md), DHT polling intervals adapt dynamically to user and device context:

| State | Base Interval | Activation Conditions | Control Mechanism / Loop |
| :--- | :--- | :--- | :--- |
| **`FOREGROUND_CHAT`** | 10 seconds ($\pm 30\%$ jitter) | Screen ON + App in Foreground + Active Conversation Window (`activeChatContactId != null`) | In-process Coroutine Loop (`AdaptivePollingManager`) |
| **`APP_ACTIVE_OTHER`** | 60 seconds ($\pm 30\%$ jitter) | Screen ON + App in Foreground + No Active Chat (contacts list, diagnostics, settings) | In-process Coroutine Loop (`AdaptivePollingManager`) |
| **`BACKGROUND_IDLE`** | 300 seconds / 5 min ($\pm 30\%$ jitter) | Screen ON + App in Background (minimized, user interacting with other apps) | In-process Coroutine Loop + AlarmManager fallback |
| **`DOZE_SLEEP`** | 900 seconds / 15 min | Screen OFF (device locked / sleeping, Doze mode) | Coroutine loop paused; driven strictly by `AlarmManager.setAndAllowWhileIdle` + `WorkManager` |

### Truth Table (Deterministic State Resolution)

State resolution is a pure deterministic function `AdaptivePollingManager.resolvePollingState`:

$$\text{PollingState} = f(\text{isScreenInteractive}, \text{isAppForeground}, \text{activeChatContactId})$$

| `isScreenInteractive` (Screen) | `isAppForeground` (App) | `activeChatContactId` (Chat) | State Machine Result |
| :---: | :---: | :---: | :--- |
| **`false`** | *any* | *any* | **`DOZE_SLEEP`** (15 min) |
| **`true`** | **`false`** | *any* | **`BACKGROUND_IDLE`** (5 min) |
| **`true`** | **`true`** | `null` | **`APP_ACTIVE_OTHER`** (1 min) |
| **`true`** | **`true`** | `ID != null` | **`FOREGROUND_CHAT`** (10 s) |

### Lifecycle Defect Remediation (Screen and Activity Decoupling):
* **Original Defect:** Mapping `ON_STOP` of an individual `Activity` directly to screen-off (`onDeviceScreenOff()`) caused premature transitions into deep sleep `DOZE_SLEEP` (15 min) whenever the user merely minimized the app while keeping the screen on (which should enter `BACKGROUND_IDLE`, 5 min). Furthermore, configuration changes (device rotation) triggered transient `ON_STOP` calls, disrupting polling.
* **Remediation in `PollingLifecycleCoordinator`:**
  1. `ProcessLifecycleOwner` monitors process-wide application lifecycle, ignoring transient activity recreation during rotation.
  2. Physical screen state is verified independently via dynamic `ScreenStateReceiver` (`Intent.ACTION_SCREEN_OFF` and `Intent.ACTION_SCREEN_ON`) and `PowerManager.isInteractive`.
  3. A single decision point `PollingLifecycleCoordinator` updates state machine inputs via `AdaptivePollingManager.updateInputs(...)`, guaranteeing thread-safe, atomic consistency.

### Constant-Budget Stratified Polling ($N_{\text{poll}} = 8$):
To prevent network adversaries from correlating query burst volumes with user conversation count:
* Every polling tick queries a rigid budget of exactly $N_{\text{poll}} = \text{N\_POLL\_TARGETS} = 8$ DHT target hashes.
* **Stratified Priority Sampling:** When active conversation tracks exceed 8, targets are selected via Weighted Fair Stratified Sampling:
  1. High priority: Currently selected contact window (`activeChatContactId`).
  2. Medium priority: Unacknowledged incoming tracks and pending lookahead slots.
  3. Low priority: Idle contact lookahead tracks.
* **Decoy Target Padding:** When active tracks are fewer than 8, remaining query slots are padded with indistinguishable decoy target hashes generated by `DecoyTargetPool`.

### Outbound Traffic Shaping & Weighted Fair Queuing (WFQ):
Outbound transmission in `OutboundPoissonQueue` integrates a 5-class Weighted Fair Queuing (WFQ) scheduler:
1. `DIRECT_TEXT` (Priority 1)
2. `DIRECT_ACK` (Priority 2)
3. `GROUP_TEXT` (Priority 3)
4. `IMAGE_CHUNK` (Priority 4)
5. `COVER_DUMMY` (Priority 5)

* **Scheduling Frame:** Packets are dequeued according to an 8-slot deterministic pattern:
  `[DIRECT, GROUP, DIRECT, GROUP, DIRECT, IMAGE, DIRECT, COVER]`
  guaranteeing 50% bandwidth for direct messages, 25% for group messages, 12.5% for image transfers, and 12.5% for continuous background cover traffic.
* **Poisson Intervals:** Delays between outbound packet transmissions are governed by an exponential distribution $\Delta t = -\frac{1}{\lambda} \ln(U)$, ensuring packet emissions resemble a memoryless Poisson process.

## 2. Behavior under Android 12+ (API 31+) — Cached App Freezer (CAF)

### Cached App Freezer Mechanism:
Beginning with Android 11 (experimental) and Android 12+ (default standard), the Linux kernel **cgroup v2 freezer** (`/sys/fs/cgroup/uid_.../cgroup.freeze`) is enforced by Android.

When an application process moves to the cached state (`CACHED_APP` — no visible activities, no active Foreground Service with WakeLock), the OS freezes all process threads within 10–60 seconds:
* JVM threads and Kotlin coroutines (`delay()`) cease receiving CPU time.
* UDP and TCP sockets stop processing incoming socket buffers.
* A standard `delay(300_000L)` coroutine loop in `BACKGROUND_IDLE` **will not fire on schedule** until unfrozen by an external system event.

### Thawing Architecture in PQChat:
1. **Unfreezing via `AlarmManager.setAndAllowWhileIdle`:**
   * When transitioning into `BACKGROUND_IDLE` or `DOZE_SLEEP`, a `DhtAlarmReceiver` alarm is registered.
   * Alarms with `RTC_WAKEUP` and `setAndAllowWhileIdle` wake the process from frozen cgroups even during deep Doze.
   * `DhtAlarmReceiver` immediately acquires a `PARTIAL_WAKE_LOCK` (up to 30 s), preventing refreezing while KRPC DHT queries and message retrieval complete.
2. **Periodic WorkManager Maintenance (`PollingWorker`):**
   * Every 15 minutes (minimum allowable WorkManager interval), Android runs `PollingWorker` with `NetworkType.CONNECTED` constraints.
   * This wakes the process within system maintenance windows, syncing the outbox and retransmitting packets via Exponential Backoff.
3. **Immediate User Event Thawing:**
   * Turning on the screen (`ACTION_SCREEN_ON`) or reopening the app (`ProcessLifecycleOwner.ON_START`) immediately unfreezes the process, synchronously re-evaluating state in `PollingLifecycleCoordinator`.

## 3. Android 15 `dataSync` Foreground Service Limits (targetSdk 35)

### Android 15 (API 35) System Restrictions:
In Android 15 (API 35), Google introduced strict execution quotas for `dataSync` Foreground Services (`FOREGROUND_SERVICE_TYPE_DATA_SYNC`):
1. **Execution Budget:** Maximum **6 hours cumulative runtime in any rolling 24-hour window**.
2. **Timeout Handling (`onTimeout`):**
   * When the 6-hour budget expires, the OS invokes:
     ```kotlin
     Service.onTimeout(startId: Int, fgsType: Int)
     ```
   * The app has a few seconds to call `stopSelf(startId)`.
   * Failing to stop promptly causes the OS to throw an uncatchable `ForegroundServiceDidNotStopInTimeException`, crashing the process.

### Implementation in `ChatHeadService`:
1. `ChatHeadService` overrides `onTimeout(startId, fgsType)`:
   * Logs a diagnostic warning.
   * Cancels active coroutine polling jobs.
   * Calls `stopSelf(startId)`, ensuring a clean shutdown without ANR or crash.
2. **Architectural Separation of Concerns:**
   * `ChatHeadService` is strictly an **optional convenience feature** for users wanting a persistent visual P2P connectivity indicator.
   * Fundamental background messaging **does not rely on a persistent Foreground Service**, but on `AlarmManager.setAndAllowWhileIdle` and `WorkManager`. This guarantees 100% compliance with Android 15 quotas and Google Play policies.

## 4. Boot Recovery Architecture (`BOOT_COMPLETED` and WorkManager)

### Post-Reboot Task Loss:
1. All `AlarmManager` timers are **purged from OS memory** upon device shutdown or reboot.
2. The application process is not automatically launched at boot unless registered via a broadcast receiver.

### Dual-Layer Recovery Pipeline:

```
[ Device Reboot / BOOT_COMPLETED ]
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
 [ WorkManager workdb ]    [ BootReceiver ]
         │                   │
         ▼                   ├─► Re-enqueue PollingWorker
 Automated restart           ├─► Reschedule AlarmManager Doze Alarm
 of periodic tasks           └─► Restore Pending Republish Tasks
 in background (SQLite)
```

1. **`BootReceiver` (`android.intent.action.BOOT_COMPLETED` & `ACTION_MY_PACKAGE_REPLACED`):**
   * Declared statically in `AndroidManifest.xml` with `RECEIVE_BOOT_COMPLETED`.
   * Upon boot, invokes `goAsync()` on `Dispatchers.IO`:
     - Restores Doze alarm via `PollingScheduler.scheduleNextDozeAlarm()`.
     - Validates and resumes pending Room outbox republish schedules (`applyRepublishSchedule()`).
     - Re-enqueues `PollingWorker.enqueuePeriodicWork(context)`.
2. **Internal WorkManager Persistence:**
   * Periodic work queued via `WorkManager.enqueueUniquePeriodicWork` with `ExistingPeriodicWorkPolicy.KEEP` is persisted in WorkManager's SQLite database (`androidx.work.workdb`).
   * `androidx.work` maintains its own internal `RescheduleReceiver` that resumes scheduled tasks across device restarts.
